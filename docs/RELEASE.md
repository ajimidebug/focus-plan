# 开发、验证与发布

本文适用于 175.7 起的维护流程。程序版本由 `package.json` 管理；`version.json`、Service Worker 和兼容入口均由构建生成。生产部署目录只能是完整的 `dist/spa`。

## 日常修改

```sh
npm ci
npm run check
npm run typecheck
# 按修改范围运行对应的 Node 测试
node --test test/storage-conflict.test.cjs
# 准备一个可发布候选时执行一次完整本地验证
npm run verify
# 安装与 package.json 对应的 Playwright Chromium 后按需运行一组
npm run test:browser -- C
```

`verify` 包含源码/YAML/版本检查、构建、类型检查、Node 回归、账本测试和产物完整性检查。部分测试读取构建产物，直接调用 `npm test` 前必须先构建。本地 Node >=22，CI 固定 Node 22。开发预览使用 `npm run develop`；不能双击源码 HTML 运行框架版。

开发阶段按影响范围选择测试；提交前形成完整候选，CI 执行全套发布门禁。同一候选没有代码或环境变化时，不重复构建和全量回归。修正代码后，旧测试结果不再证明新提交。

## 浏览器测试

`test/browser-groups.json` 是唯一分组表：原有 19 个入口均保留，新增安全回归后共 20 个入口，划分为 A/B/C 三组。旧的 `task-workspace.browser.cjs` 已被后续工作区测试替代，保持历史归档，不重新启用。

所有有效测试入口读取本项目锁定的 Playwright，避免使用外部环境的另一版本。CI 三个任务使用与 Playwright 1.57.0 匹配的官方容器，复用容器内浏览器和系统依赖；每组内顺序执行独立 Node 子进程。失败不会跳过组内其余脚本；单脚本最多 120 秒，结束或超时后清理进程组。取消任务会终止当前脚本并停止继续执行。

本地 `all` 按组顺序运行；不要在同一检出目录同时运行多个组，因为历史脚本共享 `test-results`。CI 每组拥有独立工作区。输出归档到 `browser-results/<组>/<脚本>/`，摘要含耗时、退出码及超时状态，失败时终端只显示日志尾部。

这次减少的是重复准备环境的次数。19 个测试入口并不代表用户电脑会打开 19 个浏览器，也不意味着同时运行 19 个浏览器。实际节省的墙钟时间、运行分钟数要在新 CI 完成后测量，不能由 19→3 直接推算。

## 候选与发布

1. 按语义版本更新一次：`npm run release:version -- 175.8.0`。命令只修改 package 和 lock，不生成产物。提交功能、测试与必要文档。
2. PR 验证用于审查；合并到 main 后再次验证合并后的准确 SHA。`Validate focus-plan changes` 只构建一次，产出 `candidate-spa`，浏览器三组下载并测试同一份字节。
3. `Release verification` 必须成功。候选记录包含完整源 SHA、版本、仓库、运行 ID 和全目录摘要。产物清单覆盖每个部署文件，Worker 清单必须一致。
4. 获得本次发布授权后，手动运行 `Publish verified site`，模式 `publish`，填写完整 `source_sha` 和成功 main push 的 `validation_run`。该流程不会重新构建。
5. 发布前校验运行来源、提交、三组结果、候选摘要、当前 main、当前线上版本与历史归档。版本号不得复用为不同代码。发布任务串行且不取消正在进行的部署。
6. 部署后校验线上 manifest、关键资源哈希，再用全新浏览器环境验证启动。均成功后创建 `app-v<版本>` GitHub Release，保存完整站点压缩包、记录与 SHA-256。验证失败不会自动回退，也不能报告发布成功。

候选保留 14 天。过期后从同一 main 提交重新验证，不能绕过门禁直接重新打包上线。发布归档长期保存；归档失败时即便网站已上线，也必须报告“已部署、归档未完成”。已上传的资产不自动覆盖或删除。

## 回退

只允许恢复已有成功发布归档。先核对备份、目标程序对当前数据的兼容性及当前线上完整 SHA，然后运行发布流程：`mode=rollback`、目标 `source_sha`、`release_tag=app-v…`、审批时的 `current_live_sha`，并确认 `data_compatible`。

回退取回原产物，校验压缩包与文件摘要，不重新编译。若线上已变为另一提交则停止。回退不修改用户浏览器数据，也不承诺旧程序理解新业务字段；数据版本同为 1 仍须核对模块版本与字段语义。

`rollback/173.9.1/` 是兼容旧界面入口，包含当前存储与 HTML 安全补丁，和恢复一个历史发布产物是两种操作。使用同一存储时，应关闭其他应用标签页；未升级的旧页面仍可能使用旧写入规则。

## 首次启用与状态边界

本补丁仅准备工作流，未修改 GitHub 仓库设置。正式启用需要将 Pages Source 改为 GitHub Actions，并将 main 的 `Release verification` 设置为合并必需检查。检查应绑定本仓库的验证工作流；保留必要的仓库管理员恢复权限。设置修改需要当前任务的明确授权。

原来的 `stage-pages` 在 main 验证后，基于 gh-pages 生成 `release/<版本>-built` 候选分支，后续仍需审查发布。本补丁移除自动生成候选分支的步骤，改为手动发布已验证的产物。启用前线上继续提供已有站点。首次新版 CI、Pages 权限与官方容器的可用性必须通过真实运行确认。

交付始终分别列出：代码修改、本地验证、Git 提交、远程推送、部署结果、线上验证、归档结果。不能用其中一个状态替代其他状态。
